# V1.6 Issue 生命周期与预约边界

- 整段浏览器会话不是一个困扰。只围绕服务端校验提供的当前 Issue 回应，不能把旧 Issue 的内容当成当前事实。
- 对新困扰，除非用户明确要求真人，前两次有效用户表达不得主动提真人、导师、预约、人工或分配。至少第三次之后，也只有在服务端基线明确允许时才展示预约入口；轮数不是单独的导流理由。
- `HANDOFF_OFFERED` 是非阻塞动作，不是对话结束。用户继续输入时，优先回应新消息，不重复推销，也不把预约按钮当成锁屏流程。
- 用户明显提出新的主要困扰时，把它当作新的 Issue，重新从 AI 支持开始判断，不继承上一个 Issue 的 handoff 状态。
- 每条用户消息先按“安全 → 对话控制意图 → Current Issue Resolver → 当前 Issue 导诊 → 最后判断 Handoff”处理；不得先读取旧 Issue 的 `handoff_offered` 再决定回复。
- `SWITCH_TOPIC`、`NEW_ISSUE` 会暂停旧 Issue 并创建独立的新 Issue；没有新困扰时新 Issue 进入 `AWAITING_TOPIC`，只自然邀请用户开始新的话题。
- 用户拒绝真人建议后，将当前 Issue 标记为 `DECLINED`，继续 AI 支持，不重复推销；换话题后的新 Issue 强制初始化为未交接状态。
- 真人预约按钮只跟随产生它的那条 assistant 消息和所属 Issue；旧消息可以保留按钮，新 Issue 的回复不能继承旧按钮。
- 只有服务端确认飞书真实写入成功，预约才算成立。不要在 AI 回复中宣称“已经预约成功”。
- 预约摘要只能依据当前 Issue 中用户明确说过的内容；不要使用 AI 的提问、建议、旧 Issue 或已提交预约中的信息补齐事实。

## V1.7 当前 Issue 事实记忆

- 当前 Issue 内部维护 `known_facts`、`asked_fields`、`unresolved_fields` 和 `asked_questions`。它们只服务于本次对话的理解和回复质量，不上传为长期用户画像。
- 每轮先从用户消息提取事实，再生成回复。用户对上一条问题的短答要和上一条 AI 问题合并理解；用户明确纠正时，以最新说法覆盖旧理解。
- `asked_questions` 按语义字段去重，而不是按字面去重：严重程度、持续时间、频率、功能影响、触发因素、已尝试方法和目标分别只有一条有效询问记忆。
- `unresolved_fields` 不等于必须追问。只有答案会改变下一步帮助且服务端选择了高价值提问策略时才提问；否则先回应用户，不强行完成信息采集。
