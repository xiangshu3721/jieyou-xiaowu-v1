## 0. 保真：原典、旧产品规则、新产品解释分开

**原典原意（仅为定位和简述，不取代原文）：**
1. “每次卡牌个案只看一个具体清晰的问题，聚焦一个点”。
2. “聊的过程中，客户会跑偏，整个探索过程中的聚焦一样重要”。

以上两句出自原始《镜像技术》第 4 页。**原始场景是卡牌个案**，不是 AI 可以随意宣称用户“跑偏”或强制只能聊一个 Issue 的理由。

**旧版 V1.2 产品化**：每次确定一个主问题；“跑题时温和拉回”，不同时分析所有人生问题。但 V1.2 以导诊与分流为主，属于历史产品设计，不覆盖最新明确需求。

**V3 的新增适配决定（提案，非原典引文）**：
- 聚焦是**帮助探索者自己辨认此刻最想看的一个焦点**，而不是 AI 指定“正确问题”。
- 当前焦点是**可变的工作假设**，允许未定、允许多条线索共存、允许用户自主换题。
- 要同时区分“用户深入同一问题的不同侧面”与“真的选择了新话题”；不能把所有关联联想都叫跑偏。
- 开放式提问用于帮助用户自己聚焦，**不是**逼迫填写一个固定 Problem Map 或任意限制轮数。
- 深层创伤探索、医疗专业和危机处理遵守更高优先级边界。

## 1. 功能定义与边界

| 条目 | 明确职责 |
| --- | --- |
| 核心目标 | 帮用户**自主找到或调整**当前值得探索的焦点，减少对话散乱和失联 |
| 作用对象 | 当前 Issue 的临时探索焦点，不是用户人生目标的永久标签 |
| 不负责 | 诊断、提出行动方案、把用户推给真人、判断困扰已经解决 |
| 与 JTBD 的关系 | 当前任务可为 J1 倾诉、J2 理解、J3 自寻下一步等；聚焦是可选方法而非独立用户任务 |
| 与开放提问的关系 | 可以用一个开放问题澄清重点，也可以镜像、简单确认、暂不聚焦 |
| 与 Issue 的关系 | Issue 标识谈论的困扰主题；focus_id 指代该 Issue 下当前可变的探索焦点 |
| 与事实记忆的关系 | 只保存用户确认过的焦点；AI 提出的候选必须标注为尚未确认 |

## 2. 输入 / 输出契约（设计数据，不是已经实现的 API）

**输入**：
- current_issue_id、issue_status；当前用户输入及当前轮真实意愿；
- known_facts（已确认事实）、candidate_focus（尚待确认的假设）；
- last_confirmed_focus、recent_user_corrections、asked_questions；
- latest_jtbd、selected_dialogue_act、安全/专业/预约/拒问边界；
- 当前用户提出的新议题线索及其与旧 Issue 的关系（明确/不明）。

**建议输出**：
~~~json
{
  "method_id": "MM-02",
  "policy_rule_id": "APP-FOCUS-01",
  "focus_decision": "KEEP | INVITE | CONFIRM | REVISE | SWITCH | DEFER | SKIP",
  "current_focus_status": "UNSET | CANDIDATE | USER_CONFIRMED | USER_REJECTED",
  "focus_evidence": "脱敏轮次或事实 ID；不可暴露敏感原文",
  "focus_topic": "用户已确认的焦点，未确认时为 null",
  "candidate_topic": "待用户确认的简短候选，可能为 null",
  "dialogue_act_hint": "ASK_OPEN_QUESTION | REFLECT | CLARIFY | RESPECT_BOUNDARY",
  "reason_code": "内部规则原因编码"
}
~~~

**禁止推断**：仅凭用户的长段文字、重复用词、提及新话题，就宣布焦点已确认或旧 Issue 已结束。焦点变更、Issue 切换与 Issue 关闭由各自模块处理，聚焦不能直接修改生命周期。

## 3. 应用规则卡（APP-FOCUS-01 的子规则）

| 子规则 ID | 触发和证据 | 本轮应该做什么 | 不可做什么 |
| --- | --- | --- | --- |
| F01-01 初始未定 | 用户提出模糊或并列困扰，且愿意探索 | 允许开放地邀请用户指出此刻最在意的一点，或先倾听 | 不立即强制选一项、不伪造用户优先级 |
| F01-02 用户自选 | 用户明确“我更想先聊 X” | 采用 X 作为当前已确认焦点，允许后续变更 | 不再优先追旧焦点 |
| F01-03 关联扩展 | 用户补充同一主题的原因、影响、关系或感受 | 将其视为可能有价值的同题延伸，维持探索或在必要时澄清 | 不把每个关联侧面判为“跑题” |
| F01-04 疑似偏移 | 新话题与旧焦点关系不明，用户尚未表示切换 | 低介入澄清其希望接着看哪个主题 | 不静默切 Issue、不强拉旧主题 |
| F01-05 明确切换 | 用户明确“这个先不说，我想聊 Y” | 尊重切换意愿，移交 Issue 状态模块处理 | 不以“必须聚焦”为由阻止切换 |
| F01-06 否认与纠正 | 用户说“不是 X，是 Y” | 废弃未确认 X，依照其纠正更新焦点 | 不与用户争辩、不继续围绕 X 追问 |
| F01-07 拒绝聚焦 | “我现在只想说，不想选哪个更重要” | 允许继续 J1 倾诉，不继续施加聚焦压力 | 不重复发“你到底选哪一个” |
| F01-08 出现新发现 | 用户表达“我现在发现真正困扰的是 Y” | 作为用户新的焦点/可能理解进展，必要时自然确认 | AI 不擅自宣称问题已经解决 |
| F01-09 没有必要 | 已有清晰用户焦点、对话正在产生价值 | KEEP 或 SKIP，不重复执行聚焦 | 不为了调用一种方法而增加一轮问题 |
| F01-10 高优先边界 | 安全、专业、明确真人、暂停/结束等条件生效 | 交还高优先级模块处理；DEFER/SKIP | 不把普通聚焦放到安全/服务边界之前 |

**优先级**：安全/专业限制 > 用户当前明确拒问/暂停/结束/真人意愿 > 当前用户明确切换或纠正 > 普通探索是否需要聚焦 > 语言表达偏好。

## 4. 一轮聚焦的决策图

~~~text
用户输入 + 当前 Issue 上下文
             |
   是否命中更高优先级边界？
     | 是                 | 否
  DEFER/SKIP        用户最新意愿是什么？
                     |
          +----------+-------------------+
          |          |                   |
       明确选 X    明确换 Y           不明确
          |          |                   |
        CONFIRM     SWITCH        是否已有有效焦点？
                                      | 是         | 否
                                  KEEP/SKIP   用户愿意探索吗？
                                              | 否       | 是
                                            DEFER    INVITE（开放邀请）
                                                   |
                                          等用户确认再标 USER_CONFIRMED
~~~

**实现提示**：这只是行为流程，不要求另建模型、多次 LLM 调用或专用数据库；可以由现有 JTBD/Issue 决策合同选择方法。

## 5. 自然表达：是示例，不是模板

| 情况 | 可接受的产品化问法（新例，不是原典引文） | 不可接受的方式 |
| --- | --- | --- |
| 多件事交织 | “这些事里，最近哪一件最让你放不下？” | “必须先选一个，否则没法继续” |
| 用户模糊探索 | “你说的‘摸着石头过河’，最近最让你没底的是什么？” | “你就是急于见成果” |
| 用户主动改焦点 | “原来你更想谈的是方向感。这个担心是从什么时候开始变明显的？” | “我们继续把工作压力聊完” |
| 用户拒绝聚焦 | “好，你慢慢说，我跟着听。” | “那还是先选一个最重要的” |
| 用户明确要 AI 提问 | “你刚说自己着急，这份着急最近最常出现在哪件事上？” | “可以问。”、“我先听着不必回答问题” |

**评估目标**：问得是否开放、事实是否对齐、是否尊重用户决定。不是“每轮一个问号”或“有选择题就算聚焦”。

## 6. 不可混淆的状态与异常

- **FOCUS_UNSET**：尚无明确焦点 ≠ 用户没有求助需求。
- **FOCUS_CANDIDATE**：AI 猜测可能的主题 ≠ 用户确认。
- **FOCUS_CONFIRMED**：用户选择一个焦点 ≠ 必须聊到解决才允许换题。
- **FOCUS_SWITCH**：用户选择新议题 ≠ 旧问题已解决/可以强制关闭。
- **FOCUS_DEFER**：用户不想聚焦 ≠ AI 应拒绝继续交流。
- **FOCUS_AMBIGUOUS**：新线索与当前 Issue 关系不明 ≠ 自动新建 Issue。

建议 reason codes（待代码设计定稿）：FOCUS_INVITE_MULTIPLE_TOPICS、FOCUS_USER_SELECTED、FOCUS_CONTEXT_EXPANSION、FOCUS_SWITCH_EXPLICIT、FOCUS_CORRECTION、FOCUS_DECLINED、FOCUS_HARD_BOUNDARY、FOCUS_NOT_NEEDED。

## 7. 输出校验与追踪

**局部验收**：
1. INVITE/CLARIFY → 在允许问句且已选择发问动作时，最终可见回复包含**真实开放问题**，不只是“我可以问”。
2. 用户确认 X → 当前 focus 记录可追溯用户证据；不得记录 AI 猜测为 USER_CONFIRMED。
3. SWITCH → 按 Issue 生命周期路由，绝不在此卡片直接修改旧 Issue 的 CLOSED/RESOLVED。
4. DEFER/SKIP → 不因“方法没有执行”而给模型套话或空洞复述。
5. 模型正文与 fallback 使用**同一 focus_decision 和 DialogueAct**；不得重新凭关键词“怎么办”作决定。
6. 追踪仅存 rule_id、决策码、匿名 Issue/轮次关联和版本，不默认存原始敏感对话。

**已知不可自动保证**：完全开放与自然度、提问真正有价值、是否有“温和控场”感，需要多轮人工体验评价；正则验证和 Mock 均不能 100% 证明。
